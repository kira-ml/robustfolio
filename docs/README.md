# robustfolio Documentation Index

**Version:** 1.21
**Status:** Active
**Last Updated:** 2026-10-18

This folder contains the foundational contracts, protocols, and decision records for the `robustfolio` project.
The purpose of this documentation is to **prevent predictable failure modes** before writing code: unclear objectives, data leakage, overfitting, unrealistic cost assumptions, scope creep, and unfalsifiable claims.

Read this file first. It is the map and status board for all project documentation.

---

## Documentation Principles

1. **One decision per document.** If a document answers multiple unrelated decisions, split it.
2. **Status is explicit.** Every document must declare: `draft`, `active`, `frozen`, or `retired`.
3. **Freeze before experiments.** Evaluation protocols, data contracts, cost models, and kill criteria must be `frozen` before running any experiment that tests a hypothesis.
4. **No duplication.** If a topic is covered elsewhere, link to it instead of repeating.
5. **Update the log.** Every major change to a frozen document requires a decision log entry.

**Design diagnostics status (2026-10-17).** [`../notes/power_and_effective_bets_2026-10-17.md`](../notes/power_and_effective_bets_2026-10-17.md) v1.1 and [`../scripts/diagnostics_power.py`](../scripts/diagnostics_power.py) measure two properties of the data and the test design, and are **not an experiment and not a registry entry** (protocol §12.2): no portfolio is formed and no strategy metric is reported, so nothing here counts toward the multiple-testing denominator or can be cited for or against H1–H3. The 18 candidates carry only **3–5 independent directions** (`N_part` 3.14 / `N_ent` 5.03; per-fold 2.45–3.91 / 4.13–5.71), and **12 of 18** sample eigenvalues fall below the Marchenko–Pastur lower edge (0.452) for an independent 18 × 168 panel — the smallest by 85× — so the H1 premise is **supported by the data rather than assumed**. The level test needs an annualised Sharpe of ≈ 0.67; the paired difference test detects the §6.2 threshold of 0.20 at ≥ 80% power once **ρ ≥ 0.98**. **F15** is resolved accordingly: ρ(candidate, best baseline) is reported in a design appendix, no registration is amended, and `N = 1` is unchanged. The earlier claim that the project is underpowered for a 0.2 Sharpe claim is **retracted**.

**Engine core status (2026-10-17).** The Phase 2 rewrite has begun with the estimator/optimizer core rather than the harness, because every defect in the project's history lived at that boundary: the SLSQP fallback, the expanding window inside the test period, and the fair-comparison defect where the cap applied to some methods and not others. `src/robustfolio/optimize.py` is now `cvxpy` + `CLARABEL` with **no fallback path** (§5.7): a non-accepted solve raises. Because CLARABEL exposes no duality gap, the §5.6 acceptance is enforced by a **KKT residual computed from the primal solution alone**, which is an equivalent certificate for a convex QP and independent of the solver. Three values the frozen documents cannot supply were raised and resolved by DEC-20261017-029: **F16** (sklearn's Ledoit-Wolf base uses `ddof=0` while §4.2 pins `ddof=1`, so M1 differs from B3 by shrinkage *and* a 1.7% scale factor — left as specified, quantified, not silently corrected); **F17** (§5.6 pins "solver defaults" *and* a 1e-7 residual; the defaults deliver 1.2e-4, so an explicit `SOLVER_TOL = 1e-14` is required, and tightening past it degrades the solver); **F18** (the initial `w⁻` is unpinned — the period starts flat at `w⁻ = 0`). A defect in the certificate itself is also recorded: the multipliers of the maximisation were first added rather than subtracted, which would have made the certificate accept whatever the solver returned. Evidence: `scripts/certify_engine.py` certifies **168 rebalances × 6 solver-backed methods = 1,008 solves with zero failures**, worst KKT residual `2.97e-11` (3,400× inside the acceptance threshold), `cond(Σ̂)` `1.30e4`–`6.09e5`. Risk parity's cap binds on **154 of 168** rebalances, so B2 is box-constrained by a convex homotopy rather than a cap on unnormalised weights. The walk-forward harness followed the same day — see the next paragraph.

**Harness and certificate status (2026-10-17).** The walk-forward harness (spec §6) lands in `src/robustfolio/backtest.py`, with `tests/test_backtest.py` covering the leakage-critical behaviour: no look-ahead under an exact-equality check, drift applied before the universe change, turnover computed over the full candidate universe, and folds as 12-month blocks of the rebalance index. The cost model cannot reach the optimiser — each rebalance is solved once and every cost level is derived from that single turnover series — so a cost level cannot influence the weights it prices. `scripts/certify_engine.py` no longer rebuilds the rebalance loop; it **drives the harness**, so the evidence is produced by the artifact under test. The rewritten engine **certifies the entire frozen run: 7 methods × 168 rebalances = 1,176 solves, zero rejections**, worst KKT residual `1.49e-11` (≈ 6,700× inside the acceptance threshold); B5's worst residual fell from `5.1e-7` to `2.1e-12`. Five findings are recorded by DEC-20261017-030. All are implementation-level and none amends a frozen document: **F19** (estimator results depended on the pandas frame's *memory layout* — a ULP-level nondeterminism that would have falsified §5.4.8 and could have let the leakage suite report its own floating-point perturbation as leaked information; fixed by a contiguity guarantee, verified bit-identical to the pinned pandas definitions); **F20** (the certificate recovered the sum multiplier `nu` from the *smooth interior* indices and fell back to `nu = 0` when that set was empty — which happens precisely when the turnover penalty makes *holding* optimal, so it rejected **seven optimal B5 rebalances** with residuals up to `1.5e-3`; replaced by an exact interval formulation that needs no subset); **F21** (a mathematically redundant `nonneg=True` bound on the L1 auxiliary variable changed CLARABEL's constraint matrix and its path, making it return `optimal_inaccurate` at a point `2.8e-11` below the optimum on one rebalance — the certificate caught it, and the bound is removed); **F22** (risk parity's uncapped branch never ran the §5.6 acceptance checks at all — **14 of 168** B2 rebalances were silently uncertified); and **F23** (the certification script had been certifying a *different* B5 problem than production runs, which is exactly why F20 and F21 were invisible to it). `SOLVER_TOL = 1e-14` is re-confirmed on the whole run, and its evidence table in `config.py` now reports whole-run figures: `1e-12` leaves 15 rebalances over acceptance, `1e-13` and `1e-14` leave 0, and `1e-15` and `1e-16` leave 41 and 132.

**Reporting layer status (2026-10-17).** The execution path is complete: `src/robustfolio/metrics.py` is rewritten to the spec §7.1–§7.7 registry with one definition per metric, `stats.py` implements §§7.8–§7.11 (PSR, DSR, the stationary block bootstrap), and `report.py` produces the protocol §14 disclosure table, the sixteen-comparison §6.1–§6.4 decision table, and the per-fold, calibration and design/detectability tables. **One command regenerates the report:** `python scripts/run_experiment.py --snapshot <id> --out results/<run_id>/` writes `manifest.json` (snapshot, git commit, protocol/spec versions, seed, environment), `outcomes.csv`, `decisions.csv`, `calibration.csv`, `folds_<M>.csv` and `report.md`, re-asserting the §5.6 certificate and the §13.1 structure on the run it reports. The Phase 1 `metrics.annualized_turnover` — which derived turnover from `weights.diff()` and so ignored drift — is **deleted** as §7.2 requires, and `BacktestResult.annualized_turnover` now delegates to the single canonical formula. Three findings are recorded by DEC-20261017-031, all **open owner decisions** and none of them numeric: **F24** (§7.8 does not define the object of its prediction interval, nor the realisation of a one-month volatility — the return half is implemented under a stated reading and the volatility half is **not implemented at all**, rather than filled with a definition); **F25** (§6.3's "advantage" is not pinned to a metric and its two clauses need different properties — fold wins are counted on net Sharpe per §2 while the concentration clause uses per-fold mean monthly net excess return, and the reading **decides the verdict** in the first run); **F26** (validating the report generator required executing the frozen configuration, so Test D's answer was observed before Test D ran — the decision rule was frozen first and cannot move, but Test D is now a reproduction rather than a blind test).

The first end-to-end run is logged as **`EXP-X-20261017-003`** — exploratory, non-confirmatory, **non-counting** (§12.10). Headline net Sharpe at the 10 bps headline cost, with 90% bootstrap intervals: **`B3` (sample MVO) 0.7896** [0.3311, 1.3176] — the **best baseline**; `B5` 0.7843; `M1` 0.7860 [0.3269, 1.2980]; `M2` 0.8538 [0.4255, 1.3687]. `M2` leads the best baseline by **+0.064** (the §6.2 bar is 0.20) with a PSR against it of **0.587** (the §6.1 bar is 0.95), so **both candidates return FAILURE under §6.4**; their DSR p-values (0.0032, 0.0017) pass against a *zero* benchmark, which is precisely the contrast §6.1's two bullets exist to expose. §7.8 return-interval coverage is 81.5%–87.0% for all seven methods, inside the 80–100% target. The design/detectability appendix (finding F15, DEC-20261017-028 — **not** a registered metric) gives `rho(M1, B3) = 0.9845` and `rho(M2, B3) = 0.9856`, inside the regime where the design diagnostic found the paired test adequately powered, so the nulls are statements about the effect rather than about detectability. **No hypothesis statement follows from this run** and it fires no trigger: K1 belongs to `EXP-H2-20261017-001`.

**Release packaging status (2026-10-17).** The reproduction path is now shippable. The frozen snapshot is 2.4 MB, and it has to ship: Yahoo revises history, so a reader who runs `scripts/build_snapshot.py` in six months gets a different snapshot id and slightly different numbers, at which point "check these numbers" has quietly become "trust these numbers". `scripts/pack_snapshot.py` verifies a snapshot and writes a **deterministic** `tar.gz` (sorted members, pinned mtimes, no gzip timestamp) plus an external `.sha256`, so the published digest stays valid across re-packs of identical content — the current archive is **1.67 MB** with digest `7a3fc20991b664099ada44a308dfde57d8080994ff498e2f5a0dd98f2ecab77d`, and it now carries a generated `NOTICE.txt` stating where the third-party data came from and that the repository's MIT licence does not cover it (finding **F30**, DEC-20261017-034/035). The notice sits deliberately **outside** the hash chain, so adding it moved the *archive* digest without moving the bundle hash or the snapshot id — which is the property that keeps `manifest.json` a record about data rather than a place to editorialise. `scripts/verify_release.py` is the "check me" command: it extracts the snapshot from the archive into a temporary directory, re-runs all seven methods, rebuilds the metric table, and asserts equality against the run's `outcomes.csv` at tolerance **exactly zero**. It reports **`EXACT`, max abs diff `0.000e+00` over 18 published columns.** Two findings came out of building that loop, and both are the project's own thesis demonstrated on the verification path itself: **F27** — `manifest.json`'s `sha256` map lists **five** files while `bundle_sha256` is derived from **four** (the quality report is excluded, because it embeds the snapshot id, which is derived from the bundle hash), so the first verifier recomputed a different bundle hash and **rejected every valid snapshot**; the two sets are now separate, named functions in `data.py` (`SNAPSHOT_FILES` / `BUNDLE_FILES`) with a regression test pinning the distinction. **F28** — `pandas.read_csv` at its default settings (and at `float_precision="high"`) is **lossy by one ULP**: it returns `0.1820065203183531` where the file holds `0.18200652031835318`, so a verifier that reads the published table with defaults reports a mismatch on a perfectly good artefact. Only `float_precision="round_trip"` is exact. Both bugs produced numbers that looked like findings and neither was in the artefact. The run directory now also publishes `net_excess_returns.csv` — the exact series the primary metric is defined on — so the headline figure and any statistic a reader prefers can be computed without re-running the harness; `scripts/make_figures.py` draws the equity curve, its drawdown, and the primary metric with its bootstrap interval from the run directory alone, taking the run's exploratory/confirmatory label from the run's own manifest rather than assuming one. A `CI` workflow runs the hermetic suite on a fresh clone (data-dependent tests skip with an explanatory reason, so CI is green by construction rather than red until 2.4 MB is downloaded) and, once the release asset exists, fetches the frozen snapshot to run the full suite **and** the one-command regeneration. A third finding was found by checking rather than reading: **F29** — `docs/README.md`'s own `**Version:**` header read `1.12` while its revision history ended at `1.13`, the same drift the 1.13 row itself reports fixing for 1.11. Duplicated state drifts, so it is no longer maintained by discipline: `tests/test_docs_index.py` now asserts that the index header equals its own last revision row, that the history is monotonic, that every status-board row's version and status match the document it names, and that the two frozen contracts say *Frozen*. **Nothing has been pushed and no release has been cut.** F24, F25 and F26 remain open, so no public material may use confirmatory language.

## How to Use This Documentation

- **Before coding:** Ensure `problem_framing.md`, `scope_and_non_goals.md`, and `evaluation_protocol.md` §8 are at least `Draft`.
- **Before running a backtest:** Confirm `evaluation_protocol.md` §5.4 (data contract) and §5.5 (cost model) are `Frozen`. Log the experiment in `decision_log.md` Appendix A before execution.
- **Before comparing methods:** Ensure `evaluation_protocol.md` §§4, 6, 7, and 12 are `Frozen`.
- **Before writing Phase 2 method code:** Ensure `model_and_method_spec.md` is `Frozen` (Gate 1 entry, protocol §8.4).
- **When making a technical decision:** Record it in `decision_log.md`. If irreversible and architectural, also record it in `architecture_decision_records/`.
- **When something fails or surprises:** Update `risk_register_and_premortem.md` and `decision_log.md`.
