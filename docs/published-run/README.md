# Published run — `outcomes.csv`

**Version:** 1.1
**Status:** Frozen
**Created:** 2026-10-18
**Last Updated:** 2026-10-18

This is the **published metric table**: the seven methods' outcomes from the first end-to-end run
of the reporting layer, `EXP-X-20261017-003`, computed from the frozen snapshot
`yahoo-usetf-2007-01-01_2026-09-30-2026-10-17-2ad06139`.

It is committed, all 4,777 bytes of it, for one reason: **it makes the reproduction claim a standing
guarantee instead of a one-off.** `scripts/verify_release.py` compares a freshly computed table
against a reference table and exits non-zero on any difference, at tolerance **exactly zero**. Without
a committed reference, that check can only ever be run by a person who already has a run directory —
so CI could regenerate the numbers but never say whether they were *the same* numbers. Now it can, and
the repository's own CI runs it against the release archive:

```bash
python scripts/verify_release.py \
    --archive <the release asset> \
    --run docs/published-run \
    --expect-sha256 <the digest quoted in the release notes>
```

Expect **`EXACT`, max abs diff `0.000e+00`**.

## The equality is a property of the arithmetic, not of the machine

The first CI run of this comparison **failed**: one column, `autocorr1`, was `4.163e-17`
away from the committed value — about three units in the last place — while the other seventeen
columns the verifier checks matched bit-for-bit. Nothing was wrong with the archive or with the
code's logic. `autocorr1` was computed with `np.corrcoef`, which reaches a BLAS `ddot`/`dgemm`
kernel, and OpenBLAS selects its kernel at *runtime* from the CPU's feature set: the same bytes
and the same Python produced different last bits on a different CPU.

It is now computed with an exactly-rounded summation (`math.fsum` over the departures, plus the
primitives IEEE-754 requires to be correctly rounded), so every rounding step is defined by the
standard rather than chosen by a kernel. That is **finding F33** (`decision_log.md`,
DEC-20261018-037). Regenerating the table after the fix moved exactly one column, in its last
three bits, and no headline number: the diff is recorded in that decision.

The residual is stated rather than hidden. The estimator's covariance still goes through
`np.cov`, and so does the linear algebra behind the solver; those are matrix products whose
last-bit behaviour is not this repository's to define. What is claimed is what has been checked:
tolerance exactly zero, on two platforms, against a pinned archive digest.

## Why this is not circular

The table is a *record of an output*, not an input. Nothing in the pipeline reads it; the code
re-derives every number from the price panel in the archive. A mismatch is therefore information
about the code or the archive, never about this file — which is what makes it usable as a check.

## What it is not

**Exploratory and non-confirmatory.** These are the numbers of `EXP-X-20261017-003`, which was
executed to validate the report generator. They may not be cited for or against any hypothesis
(finding **F26**, `decision_log.md` DEC-20261017-034). The file is here to make a check runnable, not
to be a result.

The companion files a full run produces (`decisions.csv`, `calibration.csv`, `design.csv`,
`folds_*.csv`, `net_excess_returns.csv`, `manifest.json`, `report.md`) are deliberately **not**
committed: they are regenerated by one command, and `results/` ignores run directories for that
reason. Only the table the verifier compares against is pinned here.
